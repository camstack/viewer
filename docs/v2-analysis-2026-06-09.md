# camstack-viewer → v2 (camstack-only) — Analysis (2026-06-09)

Goal: a brand-new **v2** supporting **only camstack** (camstack-server hub via `@camstack/sdk` tRPC), dropping all third-party distributors (Separate NVR / External hub / RTSP). Preserve the **timeline**, **grids**, and the **camera-view overlay flags** (motion, audio, …). In parallel: design a performant **24/7 (or plugin-gated) recording**.

Stack (unchanged): Expo ~54 / RN 0.81 / React 19 universal (iOS/Android/web), expo-router, zustand, react-query, `@camstack/sdk`, react-native-webrtc + react-native-video.

---

## 1. Timeline

- **Active component = `TheaterTimeline`** (`src/components/TheaterTimeline/`). It's the ONLY timeline mounted live (in `app/(tabs)/cameras/[id].tsx`). It is **adapter-agnostic** and already works with `CamStackAdapter`.
- **Dead/legacy (drop):** `DetectionTimeline`, `DetectionTimelineV2`, `ReactScrollableTimeline`. `app/(tabs)/events.tsx` is a flat event list, NOT the timeline.
- **Tech:** `@shopify/flash-list` virtual list + precomputed heights + binary-search pixel→epoch mapping (the perf core). Heatmap bar (48 bins), continuous time cursor, zoom levels (7), recording/motion/audio bands, scrub→playback, live-edge follow.
- **Data (already camstack-wired):** `timeline.getClusteredDayData` (primary), `videoclips.list`, `playback.getPlaybackInfo` + HLS VOD, `/snapshot/.../previews` (scrub thumbs), `timeline.getDetectionClasses`, `events.getReelEvents`.
- **To strip for v2:** Separate NVR scrub controller (`use-separate-nvr-scrub-controller`, `isNvrAdapter` branch), External hub `EventsAppAuth`/`useEventsAppImageSource` (replace with `adapter.resolveAssetUrl`), `isNvrFormatVideoId`.
- **Verdict:** carry over ~as-is; remove third-party auth/scrub specifics.

## 2. Grids + camera-view flags

- **Grid model (clean, adapter-agnostic):** `GridDefinition { id, name, items:[{i,x,y,w,h}], layoutMode:'manual'|'auto' }`, persisted via `useGridStore` → settings repo (SQLite/IndexedDB). Web uses `react-grid-layout`; native uses absolute/flex + `react-native-draggable-flatlist` (edit screen). Auto-layout packs cells at 16:9.
- **Tile = `CameraStreamPlayer`** (3373 LOC) — shared between single-view and grid cells (`isGridView` prop). WebRTC live / MJPEG / rtsp / NVR MediaStream / clip URL branches. Snapshot fallback from `useSnapshotStore`.
- **Overlay flags inventory** (all driven by `ICameraSource` observables → hooks → pill components, **adapter-agnostic**):
  motion, audio (binary), dBFS/RMS sensors, object-detection count + bounding boxes, battery, recording, sleep, offline, accessory switches (light/siren/PIR/autotrack), intercom support, adaptive-quality badge, highlight glow border.
- **camstack-native status:**
  - **LIVE already:** motion (`live.onMotion`), audio + dBFS/rms (`live.onAudioLevel`), detections+boxes (`live.onDetection`), online + recording (`cameras.getStatus`), intercom (`config.hasIntercom`), adaptive quality, snapshots.
  - **MISSING server-side (gaps to close):** `batteryLevel`/`charging`/`sleep` and `accessorySwitchStates` are not yet returned by `cameras.getStatus` (adapter has the slots). Online ideally push-based instead of 10s poll.
- **Verdict:** the entire flags architecture carries over unchanged; only the **server** must populate the few missing per-camera fields.

## 3. Streaming / adapters / connection

- **Two shared-RTC systems:**
  - `sharedRtcConnection.ts` (~1200 LOC) — **100% External hub-coupled** (RTCConnectionManagement, engine.io). **STRIP.**
  - `camstackSharedSession.ts` (~250 LOC) — **camstack-native** shared PC (one PC + data-channel addTrack/removeTrack). **KEEP + harden** (it's a module-level singleton → make per-`baseUrl`; add reconnect + NVR-track support).
- **`CamStackAdapter` (1981 LOC) = the v2 foundation.** Login (`admin.login` → JWT 23h) → typed tRPC WS client (`@camstack/sdk` `AppRouter`, superjson) → streaming via the hub's `webrtc-session` cap (server-offers flow) with shared-session fast path + standalone WHEP fallback.
- **STRIP (big list):** adapters `separate-nvr.ts`/`external-hub.ts`/`rtsp.ts`; libs `sharedRtcConnection`, `browserSignalingSession`, `external-hub*`, `separate-nvr*`, `eventsApp*`, `homeassistant.ts`, `webrtcDataChannelRpc`; UI `ExternalHubCameraStreamPlayer`, `ExternalHubCredentialsPrompt`, `app/embed/player.tsx`; deps `@external-hub/client`, `@external-hub/types`; test scripts `test:nvr-*`.
- **KEEP:** `CamStackAdapter`, `camstackSharedSession` (harden), `camstackTrpcClient`, `camstack-proxy`, `iceServers`, `BaseCameraAdapter`, `ICameraSource` types, native audio modules (`modules/camstack-webrtc-audio`, `withAudioSessionControl`), all zustand stores, all non-third-party UI.

## 4. Recording — ground truth

- **App does NOT record.** Only a web-only one-shot `MediaRecorder` (`liveStreamRecording.ts`); RN returns false. No local video storage; DB caches only metadata.
- **Server HAS a full recording engine — but it's currently INERT.** `packages/addon-post-analysis` (`recording-engine` cap, 17 methods, SDK `client.system.recordingEngine`):
  - `SegmentWriter` → `ffmpeg -c copy -f segment -segment_format mp4 (+frag_keyframe…)` (codec passthrough fMP4).
  - Modes: `continuous | motion | scheduled | composite` (motion uses an in-memory pre-buffer ring → flush on event).
  - `PlaylistGenerator` (HLS VOD/live), `RetentionManager` (retentionDays/Gb), segments indexed in better-sqlite3.
  - Reads the **stream-broker RTSP restream** (consumer kind `'recording'` already exists) — zero extra camera load, near-zero CPU.
- **Critical gaps for v2:**
  1. `setRecordingDependencies(...)` is **never called** → `RecordingAddon.onInitialize` early-exits → engine inert. **#1 blocker.**
  2. **No HTTP file-serving route** for segment `.mp4`s (playlists return filesystem paths) → a mobile/web player can't fetch them. Needs an authenticated/signed-URL static route.
  3. The device-scoped `recording.cap.ts` (`getSegments`/`getPlaybackUrl`/`getThumbnailAt`) has **no provider wired** (only the system-scoped engine exists).
  4. No recording-state SDK subscription helper; no on-demand clip-export/download route.

### Recording design options (trade-offs, not yet decided)
- **A — Wire the existing continuous engine + add file-serving route.** Most leveraged: code already exists. CPU≈0 (passthrough), disk≈bitrate×cams (retention-bounded), reuses broker restream. Gap = wiring + one HTTP route + `getAvailability`/`getPlaylist` in the v2 timeline.
- **B — Motion/plugin-gated (same engine, `mode:'motion'`/`'scheduled'`).** Lower disk; generalize the coordinator's event subscription from motion-only to any capability event for "plugin-gated". Small localized change.
- **C — On-demand per-event clip writer** (`ffmpeg -ss -t -c copy`). Low disk, no scrubbing (clip-only).
- **D — Client-side `MediaRecorder`** — web-only, re-encodes, no seek. Keep only as "save this moment".
- **E — HLS playback of fMP4 segments** (AVPlayer/ExoPlayer/hls.js). 2–6s scrub latency (vs ~400ms WebRTC NVR). Pairs with A/B.
- **F — Remote/cloud storage** (`addon-remote-storage`) — off-prem backup; network-bound.

**Leaning:** A (+B for plugin-gating) on the server, consumed via HLS (E) in the app. Mostly wiring existing server code + one file-serving route, not greenfield.

---

## Key implication for v2 strategy

The app is **already ~90% camstack-native**: `CamStackAdapter` exists and the crown jewels (TheaterTimeline, grid model, CameraStreamPlayer + flags) are **adapter-agnostic and already work against the hub**. The "v2" is therefore mostly **an aggressive strip of third-party code** + closing a few **server-side gaps** (battery/sleep/accessory status fields; recording wiring + file route), NOT a from-scratch rebuild of the UI.
